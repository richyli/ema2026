🎯 學習目標（學完你能）

每條目標都是「一項能力 → 能解釋一個真實問題」。學這個不是為了學會寫程式，是為了讓沒有工程背景的你，真的做出並發布一個別人能用的小工具。目標由淺入深排列（Bloom 認知階層由低到高）。

# Bloom 層級 你會的能力 讓你能解釋的真實問題
1 應用 撰寫一份三件套規格（一句話規格／不做清單／驗證點），並 vibe coding 出可跑雛形 為什麼一開頭就叫 AI 寫 code 常常做歪？本質金句：規格留白的每一處，AI 都會用『看似合理但其實錯』的預設替你填。
2 分析 判斷 AI 產出的失敗模式（幻覺／預設亂填／改 A 壞 B／邊界爆），並用「開乾淨對話讓 AI 審計」修補 為什麼在原對話問「這有沒有問題」它都說沒事，換個全新對話一問就抓出一堆？因為模型對自己的作品評分很差。
3 評鑑 評斷一個做好的工具值不值得正式導入團隊 「做得出來」之後，主管真正難的判斷是什麼？——用「省下的時間 × 頻率 × 人數 vs 維護成本 × 出錯風險」權衡。AI 不會主動跟你說「這太貴、不該留」，那是人的工作。

對齊說明：目標 1 由「上半 Spec 先行＋活動步驟 1」帶出、由步驟 1「寫規格三件套」檢核；目標 2（分析層）由「AI 產出失敗模式與修補＋步驟 2 餵規格修補」帶出、由「開全新對話讓 AI 審計」檢核；目標 3（評鑑層）由「下半 主管評估值不值得導入」帶出，由全班一題「維護成本 vs 省下時間」與小作業反思檢核，難度對得上評鑑層。

  • 核心：用自然語言做出互動報導頁／資料視覺化／查詢小工具；資料接入、RWD、發布上線（GitHub Pages）；AI 產出失敗模式與修補。
  • 上（45′）：做出雛形。
  • 下（45′）：做完、發布；主管評估「值不值得正式導入」。
  • 小作業：完成並發布工具，寫「AI 幫我做到／我得自己補」反思。

與 AI 互動的工法：Tekton / Yingzao（Build Day 冠軍）

來源 Case - Claude Build Day Hackathon。示範「人怎麼帶 AI」而非「AI 幫你打字」。

  • 先規劃再動工：冠軍第一條建議 "Map the whole project before you build any of it." 先寫好 PRD（見 M PRD 撰寫與壓力測試 範本）＋ Notion 50 工單，才讓 AI 開始——用規格控制 AI，不是被 AI 牽著走。
  • 不信任 AI 自評，設外部驗證：PRD 白紙黑字寫「模型對自己的作品評分很差」，所以驗證者跑在全新 context window 獨立評分；自修正迴圈反覆檢查到通過 20 項測試（done.rubric.json），共 339 個增量構建階段。這是與 AI 互動的核心紀律——把把關機制設計進流程，而非事後人工抽查。
  • 用 AI 選工具、做架構決策（季軍 Custom Universe）：「Use Claude to choose tools, not just to write code」——把「要不要把 Apple RealityKit 加進 pipeline」這種決策也丟給 AI 一起想。
  • 互動練習：學生對自己的小工具，仿照寫一條 one-line 規格 + 一個「不做清單」+ 一個外部驗證檢查點，再開始 vibe coding，比較有無規格控制的產出差異。

💬 討論／分享／反思（下半尾段 10′）

  • 成果快展（每組 1–2′）：demo 自己發布的工具，講「最意外 AI 幫你做到的一件事」。
  • 全班一題（3′）：「這個東西值不值得正式導入團隊？」用一個判準回答——維護成本 vs 省下的時間。

📚 詳細上課內容

90′ practice，跨 2 個 45′ slot。核心目標：讓學生用自然語言（vibe coding）真的做出並發布一個能用的小工具，過程中體驗 AI 的失敗模式與修補。上半 45′ 做雛形、下半 45′ 發布並評估。

一、逐段講稿要點

上半 45′ — 做出雛形

開場（0–5′）：vibe coding 是什麼，不是什麼

  • 一句話定義：「vibe coding 就是你用自然語言描述你要什麼，AI 幫你把 code 寫出來；你的工作從『打字寫程式』變成『描述需求 + 判斷對錯』。」
  • 立刻校正期待，講 adaptive autonomy（適應性自主）這個核心：「重點不是把所有事都丟給 AI，而是校準何時放手、何時自己接手——能沿著自主刻度滑動的人，比固定全放手或全自己做的人，產出品質更高。」這就是今天整堂課的暗線。
  • 轉場句：「但放手之前，你得先講清楚要什麼。所以我們不是一開頭就叫 AI 寫 code，而是先寫規格。」

Spec 先行：怎麼描述需求（5–18′）

  • 核心紀律：先想再建。引 Case - Opus 4.7 Claude Code Hackathon 第三原則 Maieutic 作者「花整整兩天做設計、一行 code 都沒寫」，這個「慢」的開頭讓後面全部變快。也引 Case - Claude Build Day Hackathon 冠軍 Tekton 的第一條建議：「動工前先把整個專案規劃完（Map the whole project before you build any of it）」——先寫 50 張工單的 PRD 才讓 AI 動手。
  • 講「為什麼規格這麼重要」：AI 會用「看似合理但其實是錯」的預設值，去填補你沒講清楚的地方。你規格留白的每一處，AI 都會自作主張。所以規格是你和 AI 之間的「邊界物件」——你用規格控制 AI，不是被 AI 牽著走。
  • 教三段式好 prompt 結構（引 creativity/prompts 現成模板庫，三段式：角色設定 + 任務 + 輸出格式）。對映到今天的工具規格，給學生三個欄位：一句話規格（one-liner）／不做清單／一個驗證點。
  • 轉場句：「規格寫好了，現在才打開 AI。但你會發現它第一版常常是錯的——這不是 bug，這是常態，我們來看它會怎麼錯。」

AI 產出的失敗模式與修補（18–35′）

  • 講 cognitive offloading（認知卸載）：「AI 幫你寫 code，這叫卸載——好處是釋放你的認知資源去想更重要的事（Koh & Doroudi 2023 講適度卸載的好處）；但過度卸載你會『沒真正學到』，連哪裡錯了都看不出來。所以你不需要會手寫每一行，但你要看得懂『哪裡會出錯』。」
  • 列常見失敗模式（投影片同步）：① 幻覺出不存在的函式/套件；② 預設值亂填（你沒指定就自己編）；③ 改 A 弄壞 B（回歸錯誤）；④ 表面能跑、邊界爆掉（空輸入、超長、特殊字元）；⑤ 過度工程（給你一坨你看不懂、改不動的東西）。
  • 修補工法（這是今天最關鍵的可遷移技能）：讓 AI 自己審計。引 Case - Opus 4.7 Claude Code Hackathon 第五原則 ARIA：「建下一個功能前，先請 Claude 找出已建內容的問題」——把自我檢查設計進迴圈，不是事後人工抽查。再引 Case - Claude Build Day Hackathon：Tekton 不信任 AI 自評（PRD 白紙黑字寫「模型對自己的作品評分很差」），所以讓驗證者跑在全新的 context window 獨立評分。給學生白話版：「開一個乾淨對話，把你的工具貼進去問『這有什麼問題、哪裡會壞』，比在原對話裡問它更誠實。」
  • 也要教「敢推回」：引 Case - Opus 4.7 Claude Code Hackathon 第二原則 Wrench Board——模型說「不行」時堅持推回。校準信任是雙向的：倚賴 AI，但該覆蓋時要覆蓋。
  • 轉場句：「修補是多輪的，不是一次到位。」

迭代是常態（35–45′，接活動）

  • 講 prompt engineering：Midjourney 使用者平均跑 7.8 步迭代才得到滿意結果——vibe coding 一模一樣，你不會一個 prompt 就完工，而是「描述 → 看產出 → 找錯 → 再描述」的多輪循環。也提 Davenport 2022（Davenport Mittal 2022 How Generative AI Is Changing Creative Work）：生成 AI 需要人類在前端（給規格）和後端（驗收修補），prompt engineer 成為新職業。
  • 對映 Case - GTM Engineering at Anthropic 的 CLAFTS：「數百次系統提示迭代」才讓輸出符合本人文風——工藝在迭代，不在「一次寫出完美 prompt」。
  • 收上半場：「現在你手上有個跑得起來的雛形。下半場我們把它發布出去，讓別人能真的用——並回答一個老闆會問的問題：值不值得導入。」
下半 45′ — 做完並發布

從雛形到「能用」（0–12′）

  • 講「能跑」≠「能用」。能用要補三件事：① 處理錯誤輸入（不要使用者一打怪東西就白畫面）；② RWD（手機也能開——你的讀者一半以上用手機）；③ 一個讓人看得懂怎麼用的介面。
  • RWD 操作層用通用內容（wiki 無此操作素材，屬正常，新工具無論文）：給學生一句萬用 prompt——「請讓這個頁面在手機上也能正常顯示，用 responsive design，字級和按鈕在小螢幕要夠大」。然後在手機上真的開一次驗證。
  • 轉場句：「能用了，接下來是發布——讓它有一個網址，任何人點開就能用。」

發布上線：GitHub Pages（12–28′）

  • 操作層用通用內容（wiki 無此操作素材）。發布 checklist（投影片同步）：① 把單一 HTML 檔放進 GitHub repo；② Settings → Pages → 選 branch → 存檔；③ 拿到 username.github.io/repo 網址；④ 用手機開那個網址驗證（不是用你電腦的本機檔）；⑤ 把網址貼給旁邊同學，請他用他的手機開——別人開得起來才算發布成功。
  • 強調「為什麼選 GitHub Pages」：免費、靜態、單檔就能上、有網址可分享。對應 Case - GTM Engineering at Anthropic 的精神：先做出能分享的東西，價值才看得見。
  • 卡關預告：路徑大小寫、檔名不是 index.html、Pages 要等一兩分鐘才生效——這些都會發生，是正常的，不要慌。
  • 轉場句：「你發布了。但如果你是公司主管，你會把這個導入團隊嗎？這才是真正難的判斷。」

主管評估：值不值得導入（28–40′）

  • 這段把學生從「我做出來了」拉到「這東西在組織裡值不值得」。引 Case - Claude Build Day Hackathon 評審標準：可驗證性、真實影響力、可部署性——業界用這組標準評斷 AI 時代的好產品。
  • 給一個可操作判準（板書）：省下的時間 ×　使用頻率 ×　使用人數　vs.　維護成本 ×　出錯風險。引 Case - GTM Engineering at Anthropic 的 Sales Plugin：先在自己身上驗證（Slack 貼出 24 小時內被採用），再打包成全公司插件、數月內 80% 銷售採用——個人工具 → 驗證 → 產品化 → 分發是一條微縮生命週期。
  • 也要講 AI 沒辦法替你做的判斷（引 Case - Claude Build Day Hackathon Sim Francisco）：「AI 不會主動跟你說『這太貴了』『這不該留』，那是人的工作。」當 AI 讓『做得出來』變便宜，稀缺的就變成判斷力。
  • 轉場句：「最後五分鐘，我們把成果攤出來，講一件最意外的事。」

討論／分享／反思（40–45′）

  • 直接帶既有的「討論／分享／反思」段（見下方活動造稿）。收束回 adaptive autonomy：「今天你做的事，本質是不停地決定『這步放手給 AI，那步我自己接手』。會這件事的人，就是 AI 時代能做產品的人——而它跟你會不會寫 code，關係沒有你想的那麼大。」

四、活動與討論造稿

主活動：從一句規格做到發布（貫穿上下半場）

步驟 1（上半 35–45′）：寫規格三件套 - 指令：「打開 spec 模板，5 分鐘內填完三格——一句話規格、不做清單（至少 2 條）、一個驗證點。先不要碰 AI。」 - 給學生的提問：「你的不做清單寫了什麼？」 - 預期答案 / 常見錯誤：常見錯是「不做清單」空白或太貪心（什麼都想做）。引導句：「不做清單是在保護你——你沒寫『不做登入系統』，AI 可能就自作主張給你做一個你今天根本完成不了的登入。範圍是你定的，不是 AI 定的。」

步驟 2（下半 0–12′）：餵規格給 AI，做出雛形並修補 - 指令：「把三件套貼給 AI，請它做出單一 HTML 檔。跑起來後，開一個全新對話，把成果貼進去問：『這有什麼問題、哪裡會壞、邊界情況有沒有處理？』把它找到的問題修掉。」 - 給學生的提問：「乾淨對話找到的問題，跟你原本以為的一樣嗎？」 - 預期答案 / 常見錯誤：學生常驚訝乾淨對話「比較敢講真話」。常見卡關是 AI 越修越亂（改 A 壞 B）——引導句：「如果它越改越糟，回到上一個能跑的版本，把你要的改動講得更具體再來一次。不要在壞掉的版本上疊。」

步驟 3（下半 12–28′）：發布到 GitHub Pages - 指令：照投影片 4 的 checklist 走。驗收標準不是『我電腦上能開』，是『隔壁同學用他的手機開那個網址能用』。 - 給學生的提問（做完互換）：「換隔壁同學的工具，用你的手機開——他的『不做清單』你看得出來嗎？哪裡壞了？」 - 預期答案 / 常見錯誤：最常見是忘記 RWD（手機上爆版）、或貼了本機路徑而非 Pages 網址。引導句：「發布不是『存檔』，是『別人點得開』。你剛剛是不是在自己電腦上開的？換手機。」

收尾討論（下半 40–45′，直接用既有三段）

成果快展（每組 1–2′） - 引導句：「demo 你發布的工具，只講一句：最意外 AI 幫你做到的一件事。」 - 帶討論：點 2–3 組，把「意外」歸類——是它幫你想到你沒想到的功能（共同規劃者），還是純粹寫得快（打字機）？前者才是今天的重點。

全班一題（3′）：「值不值得正式導入團隊？」 - 引導句：「用板書那個判準回答——維護成本 vs 省下的時間。」 - 預期答案 / 常見錯誤：學生容易說「好用就導入」。回推：「好用是給你一個人好用。團隊導入要算維護成本——壞了誰修？AI 不會主動跟你說這太貴（Sim Francisco）。這個判斷沒有人幫你做。」

反思（2′，寫下） - 題目（既有）：「沒有工程背景的我，剛剛真的做出能用的東西了嗎？這改變了我對『誰能做產品』的看法嗎？」 - 引導句（收束全堂）：「對照 Case - GTM Engineering at Anthropic 那位從沒寫過 code 的銷售——他靠的不是學會寫程式，是學會校準何時放手給 AI、何時自己接手（adaptive autonomy）。你今天做的，是同一件事的縮小版。『誰能做產品』這題的答案，正在被重寫。」

小作業（既有）：完成並發布工具，寫「AI 幫我做到／我得自己補」反思——對映 cognitive offloading 的核心問題：哪些卸載給 AI 安全，哪些卸載會讓你「沒真正學到」。

連結 / 關係
